A compromised website, rebuilt with nothing left to hack

NCCMN, a national network of Christian churches and ministries, needed its website rebuilt. The backup of the old WordPress site turned out to be evidence of a compromise. This page covers what the evidence showed, why I didn't patch the old site, and how the replacement removes the attack surface instead of defending it.

  • Compromise analysis
  • Content Security Policy
  • HSTS and security headers
  • Static site build (Python, Jinja2)
  • Netlify
  • SPF / DKIM / DMARC

What the backup showed

The job started as a website rebuild. Before reusing anything from the old site, I went through the backup of it, and the first file that didn't fit was robots.txt. A small nonprofit site has one sitemap. This one advertised 86:

User-agent: *
Allow: /

Sitemap: https://nccmn.org/sitemap-index-1.xml
  …  (8 index files)
Sitemap: https://nccmn.org/sitemap4171.xml
Sitemap: https://nccmn.org/sitemap4172.xml
  …  (78 numbered sitemaps, 4171 through 4248)

That is the signature of an SEO-spam compromise. The attacker doesn't want the site's visitors; they want its search reputation. Rewriting robots.txt tells Google to crawl thousands of junk pages under a trusted domain, which then rank for whatever the spammer is selling.

The rest of the backup matched:

  • 249 junk folders holding 331 spam URLs, with random names built from obscure dictionary words and number strings (Ictonyx-282381-qjpjA, Lygodium=3&UK3g9bC=492636). By the time of the backup these returned “page not found”, so the spam content itself had been cleaned or blocked, but robots.txt was still advertising it.
  • A second, unrelated church website installed inside the same hosting account: one more install sharing the same credentials and the same exposure.
  • A heavily extended install: eight plugins and three themes, far more moving parts than an informational site needs, and every one of them something that has to be kept patched.

The backup shows what the attacker did, not how they got in, and I was careful to write it up that way rather than name a cause I couldn't prove.

Why I didn't clean the old site

The obvious move is to delete the spam, update the plugins and keep going. I recommended against it. Once an attacker has had write access to a WordPress install, you can't easily prove they're gone: a backdoor can sit in a theme file, a plugin, an upload or the database. Cleaning it means trusting that you found everything.

The site was also a poor fit for WordPress in the first place. It's informational: pages, PDFs, videos, articles, a contact form and a prayer request form. It didn't need a database, a login or eight plugins. So the replacement removes the attack surface instead of defending it.

The design principle. The safest admin login is the one that doesn't exist. A static site has no database, no PHP, no plugins and no admin page on the server, so there is nothing for an attacker to log into or exploit.

What I built

A bilingual site, Spanish first and English second, generated by a short Python build script from Jinja2 templates. The build fails and lists the problem if any internal link is broken, so a bad edit can't be published by accident.

  • Nothing reused but words and documents. None of the old code, plugins, uploads or spam pages came across. Text was carried over, and every PDF was checked for embedded scripts before it went in (none found).
  • A strict Content Security Policy. The site may only load its own scripts, styles and fonts, plus YouTube thumbnail images. There are no third-party scripts at all: no analytics, no tracking, no external fonts. The only script is a short mobile-menu toggle, and the site works without it.
  • The rest of the headers: HSTS to force HTTPS, framing blocked (frame-ancestors 'none' and X-Frame-Options: DENY), nosniff, a strict referrer policy, and a Permissions-Policy that turns off camera, microphone, location and payment features the site never uses.
  • Old WordPress doors answer “not found”. /wp-admin, /wp-login.php, /xmlrpc.php, /wp-content and the rest return a 404 immediately, so automated scanners probing for WordPress get nothing.
  • Old links still work. 75 permanent redirects send the old WordPress addresses to the matching new pages, so search rankings and bookmarks survive the move. The fake sitemaps are gone, replaced by one real one.
  • Forms without server code. Contact and prayer forms are received by the host (Netlify) with a hidden spam-trap field, and the forms ask people not to send confidential information.

One smaller decision I'm glad I made: the old tax-exemption page quoted specific IRS fines that I couldn't verify anywhere. I removed the figures and described the penalties in general terms rather than carry an unsourced number onto a new site.

The cleanup plan

Replacing the site doesn't undo the compromise. I wrote a one-time checklist for the organization so the old access is shut off as well:

  • Assume every credential tied to the old site is exposed and change it: hosting control panel, WordPress admins, FTP/SFTP, the database, and any email account that shared a password.
  • Lock down the domain: two-factor authentication and registrar lock at the registrar, and DNSSEC if offered.
  • Cut over, then remove the compromised copy: point DNS to the new host, confirm the site loads over HTTPS, then cancel the old hosting so the compromised install is gone for good.
  • Clean up search: verify the domain in Google Search Console, remove the fake sitemaps, submit the real one, and check for security warnings or manual actions.
  • Stop email spoofing: make sure SPF, DKIM and DMARC records exist for the domain.
  • Keep it safe: two-factor on the hosting account, an access review every three to six months, and a header check after every major change.

Where it stands

The replacement site is built and in final review with the organization before cutover: confirming contact details and leadership listings carried over from the old site, and supplying originals for several PDFs that the backup cut off.

What I would do differently

  • Ask the old host for server logs before cancelling the account. The backup shows what the attacker did but not how they got in or when. Access and error logs are the only thing that can answer that, and they disappear with the account.
  • Check the mailboxes as part of the incident, not after it. If a reused password was the way in, the email accounts that shared it are the next thing at risk. The checklist covers changing those passwords; I would also review their sign-in history.
  • Write a short incident summary for the board separate from the technical notes: what happened, what it means for the organization, and what it needs to decide. The checklist is written for whoever does the work, not for the people who approve it.
