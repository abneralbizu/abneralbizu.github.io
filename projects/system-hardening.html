Hardening a server and proving it worked

A neglected server carrying 46 Critical and 48 High findings, brought down to a single Medium and verified by rescan — followed by the argument that a lower number is not the same thing as a secure system.

Ninety-four Critical and High findings on a single host. That number is what an unpatched server looks like after it has been left alone long enough, and it is not unusual — it is what the estate looks like anywhere patching has quietly stopped happening.

The remediation was patching, and the verification was a rescan rather than an assumption. That second part is the habit worth having: the remediation step is where the work happens, but the rescan is the only thing that turns "I applied the updates" into evidence.

Why a smaller number is not the same as secure

This was the part of the assignment I found most worth writing about, and it is the same argument as the one in my firewall measurement project, arrived at from the other direction.

Going from ninety-four findings to one is a real improvement — those were real vulnerabilities and they are really gone. But a scan report is a measurement of what one tool, from one vantage point, with one plugin set, could observe at one moment. Several things it cannot tell you:

  • Whether the configuration is sound. A fully patched server with weak permissions, default accounts, or unnecessary services exposed will scan clean and still fall over. Patch level and hardening are different axes.
  • Whether anything is already wrong. A vulnerability scan is not a compromise assessment. Patching a host that was exploited last month closes the door and leaves whatever came through it inside.
  • What it could not see. Coverage gaps, plugins that did not fire, services that were not running during the scan window — all of it reads as absence of findings.
  • How long it stays true. One is the count as of the scan date. Next Tuesday's advisories are already being written.

So the defensible statement is narrow: as of this scan, with this tool, from this position, these specific known vulnerabilities are no longer detected on this host. That is genuinely worth reporting. It is just not the same sentence as "the server is secure," and the gap between those two sentences is where a lot of bad security reporting lives.

Beyond the operating system

Patching the OS is the first layer. Two others got attention in the same project:

The web application. A scan of the e-commerce site running in the same environment returned a High-risk finding — a reminder that a host can be fully patched while the application on top of it is not. Operating system vulnerability management and application security are separate programs that happen to run on the same hardware.

File exposure and transport. Reviewing the FTP server's exposed files, and analyzing the SSL certificate configuration, covered the two failure modes that patching never touches — data reachable because nobody set permissions, and traffic readable because the transport was configured badly or the certificate does not do what everyone assumes it does.

A control-framework reading of the same environment. Separately I mapped this environment against the Cloud Security Alliance Cloud Controls Matrix and CAIQ. PCI DSS and ISO/IEC 27001 applied and were being considered; GDPR, NIST SP 800-171 and CMMC were applicable to the business and were not addressed at all.

That is a different kind of finding from a CVE, and often a more expensive one. A scanner tells you a host is missing a patch. A controls assessment tells you an entire regulatory obligation has no owner.

What I would do differently

  • Record the specific CVEs, not just the severity counts. Counts prove a delta; CVEs prove the right things went away and let someone else verify the claim.
  • Run a configuration audit alongside the vulnerability scan — CIS Benchmark or STIG policy compliance — since that is precisely the axis a patch-level scan does not measure.
  • Investigate the one remaining Medium rather than leaving it at a count. The finding you accept should be a decision with a reason attached, not a leftover.
  • Establish a recurring scan cadence. A single before-and-after is a snapshot; vulnerability management is the loop, not the event.
