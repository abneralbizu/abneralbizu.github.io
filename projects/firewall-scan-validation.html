Measuring what a host firewall actually buys you

Everyone says to turn the host firewall on. This was an attempt to say how much it is worth, by scanning the same machine twice — once exposed, once with the firewall enabled and a scoped rule in place — and recording the difference.

The test

The target was a Windows 7 virtual machine — chosen because a legacy, unpatched host produces enough findings to make a before-and-after comparison meaningful. Two scans against the same machine, changing exactly one variable between them.

Nineteen actionable findings spanning the CVSS range down to four informational items. The SMB vulnerabilities that drove the Critical and High counts were confirmed absent on the rescan.

What the numbers do and do not mean

This is the part that matters more than the table.

The machine did not get patched. Not one vulnerability was fixed between the two scans. Every flaw present in the first scan is still present in the second — the same unpatched SMB implementation, the same missing updates, the same exploitable services. What changed is that a network-based scanner can no longer reach them.

So the honest reading of the second scan is not "this host is secure." It is "this host is no longer remotely enumerable from where the scanner was standing." Those are different claims, and conflating them is how a clean scan report becomes a false sense of safety. Anything that gets past the perimeter — a phished credential, a laptop brought back onto the network, a lateral move from a host that is reachable — finds the same unpatched machine waiting.

The other thing the comparison shows is how much a scanner depends on its vantage point. The same host, the same scanner, the same moment in time, produces a nineteen-finding report or a four-item report depending entirely on what sits between them. That is worth remembering whenever someone presents a scan as a statement of fact about a system rather than a statement about a path to it.

Where this connects to real practice. This is the same mechanism behind the scan-enablement work in my vulnerability management project — a credentialed scan cannot authenticate to a host whose firewall is blocking SMB and Remote Registry, which is why those services get opened for a scan window.

Seeing both sides of it in the same term was useful: the firewall that makes your security report look good is the same firewall that makes your credentialed scan fail. The answer in production is a rule scoped to the scanner's source address, not a disabled profile.

Triage methodology

Alongside the scanning I worked out a severity-triage approach against a deliberately vulnerable web application, because a raw CVSS score is not a priority order on its own. The questions that actually move something up or down the list:

  • Does it permit remote code execution, or something less severe?
  • What is the attack vector — network, adjacent, local, physical?
  • Is authentication required, and at what privilege level?
  • Is there a public proof of concept?
  • Is it under active exploitation in the wild?
  • Has the vendor confirmed it, and is there a patch?

Mapped against CVSS bands, that produces an order you can defend to someone asking why item four is being fixed before item two. A network-reachable, unauthenticated RCE with a public exploit outranks a higher-scoring local privilege escalation that requires an existing foothold.

What I would do differently

  • Add a third scan: credentialed, firewall on. Two scans show the network view with and without a barrier. A credentialed scan through the firewall would show what is actually installed on the box, which is the view that survives the "but it looked clean" conversation.
  • Scope the rule to a source address rather than a blanket allow, and document the revert, so the test mirrors what production would do.
  • Capture the specific CVEs behind the Critical and High findings rather than the counts alone. Counts show the delta; CVEs show whether the right things went away.
  • Test from a second vantage point — same subnet versus across the router — to show how much of the result is the firewall and how much is the network path.
